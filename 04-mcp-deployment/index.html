Deploying an MCP server

Everything so far ran on your laptop. This is what changed when the PuzzleMaster server moved to a URL that other people can reach — including the one thing that worked locally and could not possibly work in production.

~10 min live Prefect Horizon mcp-puzzlemaster.fastmcp.app Verified 2026-08-31

01 What Horizon is

Prefect Horizon is a managed platform for hosting MCP servers. If you have read anything about FastMCP Cloud, you already know it — Horizon is FastMCP Cloud, renamed and expanded. Same team, at Prefect.

That lineage matters more than a rename usually does. Prefect wrote FastMCP, the framework behind the servers in 01 and 02. The people who host the server wrote the library the server is built on, so the hosting layer is aware of what an MCP server actually is: it inspects your tools at build time and can tell you what it found.

Horizon is sold as four pillars — Deploy, Registry, Gateway, Agents. We use exactly one of them: Deploy. Everything on this page is Horizon Deploy.

The one-sentence version

You connect a GitHub repository, name a Python file inside it, and Horizon gives you an HTTPS URL that speaks MCP over Streamable HTTP. Pushing to your default branch redeploys it.

Git-backed only — there is no deploy CLI

This is the first thing that surprises people, so it is worth stating flatly. There is no horizon deploy. There is no fastmcp push. Deployment is driven by git. You connect a repo, and the act of pushing is the act of deploying.

There is a fastmcp CLI, and it does have login, logout, whoami, and inspect — but none of those deploy anything. There is also a REST API at https://horizon.prefect.io/api/v0/... authenticated with an fmcp_-prefixed bearer token, if you want to drive Horizon from CI. But the normal path, and the one we used, is: push to main.

The useful consequence: your deployment history is your git history. Every build is pinned to an exact 40-character commit SHA, resolved before the build starts. Moving a branch afterwards cannot retroactively change a build that already ran.

Pull requests get their own preview deployments at their own URLs, which is how you try a new tool without pointing production at it.

02 Preparing the repo

Horizon reads four things out of your repository. Get these right and the build is uneventful, which is the goal.

WhatOursWhy
Entrypointserver.py:mcpWhich file, and which object in it, is the server. Required — there is no default.
Dependenciesrequirements.txtAuto-discovered. Must include fastmcp.
Python version.python-version → 3.12Pins the runtime. Default is 3.12 if absent.
Committed dataenable1.txtShips inside the build artifact. Read-only at runtime, and that is fine.

The entrypoint convention

The entrypoint field uses the same syntax as fastmcp run: a relative file path, optionally followed by a colon and the name of the server object inside that file.

main.py                        # a file — Horizon finds the server object
server.py:mcp                  # explicit: the object named `mcp` in server.py
services/weather/server.py:mcp # nested is fine

The object name after : must be a valid Python identifier. The path cannot be absolute, cannot contain .., and must point inside the repository. We use server.py:mcp because being explicit costs nothing and removes a guess.

Concretely, this is what Horizon is looking for:

server.py

from fastmcp import FastMCP

mcp = FastMCP("puzzlemaster")   # <- this object, named here

@mcp.tool
def solve_wordle(guesses: list[str], feedback: list[str], agent_name: str) -> dict:
    ...
Check before you push

Run fastmcp inspect server.py:mcp locally. It prints the tools, resources, and prompts your server exposes — which is exactly what Horizon does during its build step. If inspect is unhappy on your machine, the build will be unhappy too, and finding that out locally is much faster than finding it out in a build log.

Dependencies

Horizon searches from the entrypoint's directory upward to the repository root and takes the first thing it finds, in this order:

  1. requirements.txt — installed as a dependency file
  2. uv.lock — but only when a pyproject.toml sits next to it; installed with a frozen uv sync
  3. pyproject.toml — installed as a project when it declares a build system

Whatever you use, fastmcp must be in it. Horizon relies on the FastMCP CLI to install, inspect, and run your server — even if your entrypoint is a low-level MCP server rather than a FastMCP one.

Monorepo trap

Because the search walks upward from the entrypoint, a closer but unrelated requirements.txt can shadow the one you meant. If your build installs a set of packages you did not expect, this is why. The fix is to configure an explicit dependency file path in the server settings rather than relying on discovery.

The Python version floor

Horizon resolves the Python version by walking up from the entrypoint directory looking for a .python-version file or version metadata in pyproject.toml.

This will bite you

Horizon supports Python 3.11, 3.12, 3.13, and 3.14. It does not support 3.10.

This repository targets "Python >= 3.10", and everything in 00 through 02 runs fine on 3.10 locally. That floor does not survive the move to Horizon. If you do not pin a version, you silently get 3.12 — which is usually what you wanted, but "silently" is doing a lot of work in that sentence.

.python-version

3.12

One line. Commit it. Now the runtime is a decision in your repo rather than a default you are relying on.

Why the word list is committed

enable1.txt is 172,823 words and about 1.9 MB, and it is checked into the repository. In a normal Python project you might reach for "download it on first run" or "fetch it from S3". Here, committing it is not laziness — it is the correct call, for two separate reasons.

It removes a network call from startup. Horizon warns explicitly against network calls during module import, because import happens inside a cold start and a cold start happens inside somebody's 170-second request budget. A dictionary fetched at import is a dictionary that can time out or 503 during a demo.

Committed files ship in the build artifact. The artifact Horizon builds contains your source, your installed dependencies, and everything else in the repo at that commit. So open("shared/data/enable1.txt") works at runtime, on every instance, forever — because that file was baked in at build time, not written at run time.

Hold onto that distinction. It is the whole of the next-but-one section.

03 Connecting GitHub and creating the server

UI flow described from Horizon's documentation. Field labels may have shifted since — trust the screen over this page.

  1. Sign in and create an organization

    Go to horizon.prefect.io and sign in. Horizon asks you to create an organization, which is the thing that owns your servers and their access settings. Ours is Overclock Accelerator, on the PRO plan.

    The plan matters in two specific ways later: PRO can make a server public, and PRO can invite org members. Both come back in Part 05.

  2. Install the Horizon GitHub App

    From onboarding, or later from Settings → Integrations. Horizon opens a GitHub authorization window and asks GitHub to install or configure the Horizon GitHub App.

    GitHub then asks which repositories Horizon may see — all repositories in the account, or only selected ones. Pick selected repositories and grant just the one. There is no reason to hand a hosting platform read access to everything you own, and the picker only ever shows what the installation granted.

    Where the boundary sits

    GitHub owns repository access and source history. Horizon owns the server record, the build record, the deployment URL, environment variables, access policy, and observability. GitHub credentials are never exposed to MCP clients — connecting a repo does not give the people using your server any access to your code.

  3. Create the server

    Pick the repository from the picker, then fill in:

    FieldWhat it doesOurs
    Server nameDetermines the URL. Treat it as a client-facing identifier and avoid renaming later.mcp-puzzlemaster
    DescriptionShown in the dashboard and registry.—
    EntrypointFile, optionally :object.server.py:mcp
    AuthenticationWhen on, only authenticated users in your org can connect. Horizon runs the whole OAuth flow for you.See Part 05

    The server name is the load-bearing one. It becomes https://<server-name>.fastmcp.app/mcp, that URL is stable across every future deploy, and anything pointing at it breaks if you rename.

04 Secrets

PuzzleMaster needs one secret in production: DATABASE_URL, the connection string for the Neon Postgres instance holding the audit log. It is not in the repository, and it never will be.

Why secrets never live in the repo

The obvious reason is that the repo is public. But the reason holds even if it were private, and it is worth saying out loud because "it's a private repo" is the excuse that gets people burned:

  • Git does not forget. Committing a secret and deleting it in the next commit does not remove it — it is in the history, in every clone, in every fork, and in the GitHub API. The only real remediation is rotating the credential.
  • Repo access and production access are different questions. A contractor reviewing a PR needs to read your code. They do not need your production database. Putting the credential in the source merges two access decisions that should stay separate.
  • Repos get less private over time, never more. This one went public on purpose. Plenty go public by accident.

So the credential lives in Horizon, encrypted, and arrives in the process as an environment variable. The code never sees a literal.

server.py

import os

DATABASE_URL = os.environ["DATABASE_URL"]   # set in Horizon, not in git
Small thing, real payoff

Use os.environ["X"], not os.environ.get("X"). The bracket form raises KeyError at import, which fails the build during Horizon's inspection step — you find out in a build log. The .get() form returns None, deploys green, and fails on the first tool call in front of an audience.

Setting it

Open the server, then Settings → Environment Variables → Add variable. Enter the key, the value, an optional description, and check which environments should receive it.

There are two environments, and they are separate records:

EnvironmentUsed by
ProductionDefault-branch builds and the live deployment
PreviewNon-default branches and pull request preview builds

Checking both creates one record in each with the same initial value, but they diverge from then on — updating one does not update the other. That is a feature. Point Preview at a different database than Production, so a PR that mangles the audit table mangles a table nobody cares about.

Four rules that will save you a build

  • New variables are sensitive by default. Sensitive means write-only: the dashboard will never show you the value again. Marking an existing variable sensitive is irreversible. This is correct behaviour, but it does mean you should have the value somewhere else before you paste it in.
  • Key naming is enforced. Uppercase letters, digits, and underscores; must start with an uppercase letter or underscore; 255 characters or fewer. FASTMCP_CLOUD_ and HORIZON_ are reserved prefixes. A bad key fails the build.
  • Changing a variable does not update a running server. Variables are build inputs. You must create a new build and make sure the deployment selects that artifact. Editing the value and refreshing the page achieves nothing.
  • Never print a secret. Horizon captures stdout and stderr as server logs. A debugging print(os.environ) puts your database password in a log viewer that your whole org can read. And recall from 02 that stdout is already forbidden for a different reason — over stdio it is the protocol channel.

Three secret stores, three consumers

This is the part that quietly costs a team an afternoon, so it is worth saying explicitly and early. By the end of this training there are three different places a secret can live, and each one serves a different consumer. None of them can read the others.

StoreWho reads itHoldsIn git?

claude_desktop_config.json

Locally, the repo convention is a single gitignored file at the root. Copy the template and fill it in:

cp .env.local.example .env.local
# then edit .env.local and paste your key

.env.local

ANTHROPIC_API_KEY=sk-ant-...

# Only if you point the local audit log at Postgres
# DATABASE_URL=postgresql://user:password@host:5432/dbname

A dependency-free loader at shared/envloader.py walks up from each agent to find .env.local (then .env) and populates os.environ. It never overwrites a variable that is already set, so a shell export still wins if you want to override for one run. Nothing needs exporting in the normal case.

The confusion to head off

None of these three stores can see the others. Putting DATABASE_URL in .env.local does not configure the deployed server — that file never leaves your laptop, and Horizon builds from a clean checkout of your repo, where it is gitignored anyway. Setting it in Horizon does not make your local agents work either.

The same variable name deliberately appears in two stores because the same code runs in two places. Same name, same meaning, two separate values you have to set twice. Local development points at a scratch database; production points at the real one. That is not duplication to eliminate — it is the whole reason the value is configuration rather than a literal.

The unifying rule across all three: a secret lives with the thing that consumes it, and never in the repository. The repo carries the shape of the configuration — .env.local.example, a documented variable name — and never a value.

05 Build, deploy, live URL

Once the server exists, Horizon resolves your default branch to a commit and builds. Four steps, in order:

  1. Install dependencies

    FastMCP plus everything in your requirements.txt, into a clean checkout of that exact commit. Nothing from a previous build is reused. Package resolution errors surface here, before anything is promoted.

  2. Package

    Source, dependencies, and execution configuration become an immutable artifact.

  3. Inspect

    Horizon loads your entrypoint with FastMCP and produces a manifest of the tools, resources, and prompts you expose. This is the same thing fastmcp inspect does locally.

    This step imports your module, so import-time errors and import-time side effects fail the build here — even though dependency installation succeeded a moment earlier. A missing DATABASE_URL lands exactly here.

  4. Publish and promote

    A successful build publishes an immutable artifact. A deployment then selects an artifact to serve.

The result is a stable URL ending in /mcp, of the form https://<server-name>.fastmcp.app/mcp. Ours:

https://mcp-puzzlemaster.fastmcp.app/mcp

It speaks Streamable HTTP — the transport MCP clients use over a network, and the replacement for the stdio transport every server in 00–02 used. That change is why this URL is reachable by a person with no Python installed, which is the entire subject of Part 05.

From here on, every push to the default branch triggers a new build and deployment. Pull requests get preview deployments at their own URLs.

Verified 2026-08-31

The endpoint is live. An unauthenticated request returns HTTP/2 401 with www-authenticate: Bearer realm="FastMCP" and a pointer to its OAuth discovery document — which is a server correctly refusing an anonymous caller, not a server that is down. Part 05 picks this up in detail.

06 The ephemeral filesystem

This is the part of the deployment that actually required a code change, and it is the most transferable lesson on the page. It is the moment "just write it to a file" stops working.

In 02, the audit log is SQLite, and deliberately so:

"SQLite (not in-memory) so usage survives restarts — 'monitor over time' is meaningless if the counter resets."

That reasoning is completely sound. On a laptop, SQLite is the right answer: no server to run, no credential to manage, one file, survives restarts. It is the correct engineering decision for the environment it was made in.

It cannot work on Horizon. Not "works badly" — cannot work.

What the runtime actually promises

Horizon's compute model documentation is unusually direct about this:

"Do not rely on files written during one request being available to another request. Do not rely on files written before a redeploy being available after the redeploy."

Three separate mechanisms break usage.db, and each one alone is fatal:

MechanismEffect on a local SQLite file
No instance affinityTwo requests can land on two different instances. Each has its own filesystem. Your audit trail silently forks into fragments.
Scale to zeroCompute starts on demand and goes away. The file goes with it.
Immutable artifactsEvery deploy builds a fresh artifact from a clean checkout. Anything written at runtime is not in it.

The asymmetry that makes this confusing

Read this twice

Committed files ship in the build artifact and are readable at runtime. Runtime writes do not survive.

This is why enable1.txt — 1.9 MB of dictionary, read on every single call — is completely fine, while usage.db is completely broken. Both are "just a file on disk". The difference is not size or access frequency. It is who wrote it and when. Build time, durable. Run time, gone.

If you take one thing from this page, take that. "Is it a file?" is the wrong question. "Was it written before or after the build?" is the right one.

The shape of the change

The fix is to move durable state off the local disk and into something that outlives the process. We used Neon Postgres, reached through DATABASE_URL. Here is the shape — this is the diff in miniature, not the whole file:

Local · 02

import sqlite3

DB = "usage.db"

def _conn():
    return sqlite3.connect(DB)

def log(agent, tool, inp, out, ms, ok):
    with _conn() as c:
        c.execute(
            "INSERT INTO invocations "
            "(ts, agent_name, tool, inputs, "
            " outputs, duration_ms, ok) "
            "VALUES (?,?,?,?,?,?,?)",
            (now(), agent, tool, inp,
             out, ms, ok),
        )

Horizon · 04

import os, psycopg

DB = os.environ["DATABASE_URL"]

def _conn():
    return psycopg.connect(DB)

def log(agent, tool, inp, out, ms, ok):
    with _conn() as c:
        c.execute(
            "INSERT INTO "
            "mcp_training.invocations "
            "(ts, agent_name, tool, inputs, "
            " outputs, duration_ms, ok) "
            "VALUES (%s,%s,%s,%s,%s,%s,%s)",
            (now(), agent, tool, inp,
             out, ms, ok),
        )

Read what actually changed:

  • The driver: sqlite3 → psycopg.
  • The target: a filename → a URL from the environment.
  • The placeholder style: ? → %s. A small, real annoyance.
  • The table: gains a schema qualifier, mcp_training.invocations.

What did not change: the columns, the middleware that calls log(), the tool bodies, the solvers, or usage_graph and export_results at the level of what they mean. The audit table's shape survives intact — id, ts, agent_name, tool, inputs, outputs, duration_ms, ok.

The seam again

02 put all logging behind FastMCP's on_call_tool middleware rather than decorating each tool. That decision — made for a completely different reason, so tool #6 gets audited for free — is why this migration touches one function instead of five. Centralising created a place to stand, and then a place to change.

The general rule Horizon states, and which applies to any scale-to-zero platform: store durable files outside the local runtime filesystem. Object storage for blobs, a managed database for rows. Local disk is scratch space for the duration of one request, and nothing more.

07 Observability you did not have to build

In 02 we hand-built an audit log — a middleware, a table, a graph tool, a CSV export. Horizon ships request-level observability for free. Both statements are true at once, and the honest version of this section is about what each one is actually for.

What Horizon gives you

Every MCP request passes through Horizon's gateway, which records metadata before your code runs. Three views read from that one source:

PageWhat it answers
LogsRequest by request. Method called, gateway status, timestamp, with a frequency histogram. Opening one shows the acting user or service account, the identified MCP client, request and response payloads, and what each gateway plugin did. Live-refreshing, pausable, filterable to errors only.
UsageTool calls, unique actors, error rate, and p95 latency over a window — pivoting actor ↔ tool. Select an actor to see its tools; select a tool to see its callers.
ObservabilityAggregates. Duration (avg / p50 / p95 / p99), invocations over time, and memory against allocation.

Plus two log streams attached to deployments: build logs (why a deploy never went live) and server logs (your stdout and stderr, so where your own logging and uncaught errors appear).

Retention is up to 3 days on standard plans, up to 30 on Enterprise.

A counting subtlety worth knowing

On the Observability page, an invocation is any MCP JSON-RPC message — including initialize and tools/list. A tool call is specifically tools/call. So every tool call is an invocation, but most invocations are not tool calls. If your request count looks suspiciously high, this is usually why: clients list your tools constantly.

So was 02 wasted?

No — and the reason is worth being precise about, because "the platform does that now" is a conclusion people reach too fast.

Horizon observes the transport. The 02 table observes the application.

Horizon gatewayThe 02 audit table
SeesWho called which tool, when, from which client, how long, what statusThe puzzle that went in and the answer that came out
IdentityVerified — cryptographic, from the gatewayagent_name, which the model fills in and could get wrong
Retention3 days (30 on Enterprise)Yours, forever, in your database
QueryableDashboard and REST APISQL, and a CSV you can hand to anyone

The 02 README made the claim that the exported CSV is two things at once: an audit trail, and an eval dataset nobody had to hand-write. Horizon's logs cannot be that. They do not know that "VALIDTY, center V" is an input worth regression-testing, and they age out in three days.

The honest trade: build the application-level log because it is your eval data; take the transport-level log for free because rebuilding it is a waste of your afternoon. And note the one thing Horizon has that 02 structurally could not — verified identity. 02 was explicit that agent_name is telemetry, not authentication, because a model fills it in. The gateway's actor is established before your code runs. That is the upgrade you get by moving to HTTP, and it is exactly the Depends()-shaped guarantee 02 pointed at: trustworthy because unreachable, not trustworthy because convenient.

08 Gotchas

Eight things that are obvious afterwards.

1 · The Python version floor

3.11, 3.12, 3.13, 3.14. Not 3.10, which this repo's contract permits. Commit a .python-version so the runtime is a decision, not a default.

2 · Cold starts are real

Horizon starts compute on demand and scales to zero. The first request to a fresh instance has to load the runtime, the dependencies, and your module — and for us, parse 172,823 words.

Before you demo

Warm the server with a tools/list before you present. Open the connector, or run a trivial call, a minute before you need it. The difference between a warm and a cold first response is the difference between a demo that lands and a demo where you talk over a spinner.

Structurally: keep import-time work small. No network calls at import, lazy-load anything large, cache reusable clients in module-level variables. Startup work is spent from the same 170-second budget as the request that triggered it.

3 · The payload ceiling

6 MB per request and per response — a hard ceiling inherited from AWS Lambda's synchronous invocation limit, and there is no streaming. JSON and base64 overhead eat into it further, so treat 6 MB as the wall, not the target.

This is a live concern for PuzzleMaster: export_results returns a CSV of every logged invocation. Fine today. At a few hundred thousand rows it is a tool that fails in a way nobody predicted. The documented shape is to write the export to object storage and return a URL instead of the bytes.

4 · The 170-second request timeout

Every MCP request handler has 170 seconds, measured from client through gateway to your code. Long work should return a job ID immediately and continue asynchronously. Also note: Horizon does not support long-lived GET /mcp streams for hosted servers.

5 · A green build is not a changed endpoint

The one that wastes an hour

Build success and deployment promotion are separate steps. A build can go green and the production URL can keep serving the previous artifact.

When the code is obviously updated and the endpoint obviously is not, check three things in order: was that build for a preview deployment rather than production; does promotion need to happen explicitly; and has a newer build already been selected for that deployment. It is almost always the first one.

6 · Environment variable changes need a new build

Variables are build inputs, not runtime lookups. Change one and the running server keeps the old value until you build and deploy again. Same trap as above, different door.

7 · Import-time side effects fail builds

Horizon imports your module to inspect it. Anything at module scope runs during the build — including a missing environment variable, a database connection attempt, or a file read. Dependencies installing cleanly tells you nothing about whether inspection will pass.

8 · Sessions expire after 24 hours

Gateway session routing metadata has a 24-hour TTL, and there is no affinity guarantee even inside a session. A client that has been idle overnight may need to reinitialize. This is routing state, not application state — do not store anything durable in it.

09 Recap

  • Horizon is FastMCP Cloud renamed, from the team that wrote FastMCP. We use one pillar of it: Deploy.
  • Deployment is git-backed, with no CLI. Push to the default branch. PRs get preview deployments. Every build is pinned to a commit SHA.
  • Four things in the repo: an entrypoint (server.py:mcp), dependencies including fastmcp, a .python-version, and any read-only data you want baked in.
  • Secrets go in Horizon, encrypted, per environment, and never in git — because git does not forget and repos only ever get more public.
  • Three secret stores, three consumers: .env.local for the repo's local Python agents, Horizon environment variables for the deployed server, and claude_desktop_config.json for Claude Desktop. None can read the others. The repo carries the shape of the configuration, never a value.
  • The filesystem is ephemeral. Committed files ship in the artifact and are readable. Runtime writes are gone. SQLite → Postgres was not a preference; it was the only option.
  • Horizon's observability is transport-level and free; yours is application-level and is your eval data. Keep both.
  • The limits are real numbers: 170s per request, 6 MB per payload, 1024 MB memory, 15 min build, 24 h sessions.
