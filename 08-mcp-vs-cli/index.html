MCP Training · Part 08

MCP versus the command line

Two agents, the same solver code, two different seams. We measured what each one costs in tokens, time and round-trips — and two of the three things we predicted turned out to be wrong.

~3 min live 95 runs claude-sonnet-5 2026-08-31

01 The axis

The interesting difference is not discovery. It is where capability descriptions live, and what they cost.

MCP capabilities in context

Every tool’s name, description and full JSON schema is injected into the model’s context on every request. Forty tools means forty schemas re-sent every turn — whether the model uses one of them or none.

CLI capabilities on disk

The model gets one tool definition: a generic run_command. The capabilities sit on the filesystem. The model pays only when it goes looking, roughly once per conversation rather than once per turn.

The reframe

The CLI is lazy-loading tool schemas. MCP is eager-loading all of them. Everything below follows from that one sentence.

02 What the model actually sees

Not a description read from somewhere at runtime — it ships inside the request itself. This is a real response from the deployed PuzzleMaster server:

tools/list → one entry, verbatim

{
  "name": "solve_spelling_bee",
  "description": "Solve a NYT Spelling Bee puzzle against the full ENABLE1 dictionary.",
  "inputSchema": {
    "properties": {
      "letters": { "type": "string",
                   "description": "The 7 puzzle letters, e.g. \"VALIDTY\"." },
      "center":  { "type": "string",
                   "description": "The mandatory center letter, e.g. \"V\"." }
    },
    "required": ["agent_name", "letters", "center"]
  }
}

The client calls tools/list once at connection, converts the result into the API’s tool format, and then includes it in every request for the life of the conversation.

Consequence

Tool descriptions are prompt. Three things follow: description quality is selection accuracy; descriptions written by someone else are attacker-controlled text in your context window; and every word costs tokens on every turn.

The CLI has no equivalent. There is nowhere to put a description, because there is no tool definition beyond run_command. The nearest thing is --help output — which enters context only when the model runs it, arriving as a tool result, not a tool definition. Read once, never re-sent.

The number to say out loud

Dead linear at roughly 178 input tokens per tool per request. The 37 tools that were never called cost 12,975 input tokens — paid on every single turn, forever.

Measured, not assumed

The same 37 padding capabilities were built both ways — registered as MCP tools, and generated as executables on PATH with real --help text — so both lines share an x-axis. The CLI line is flat: 2,220 → 2,220 → 2,217. Thirty-seven added capabilities moved it by three tokens.

Forty scripts and three scripts produce the identical run_command schema. Nothing about the catalogue reaches the model unless the model goes looking.

05 Composition

Task: “how many of the Spelling Bee answers are five letters or longer?” The answer is 24.

MCP 3,345 in · 428 out

Pulls all 34 words into context and counts them there. 1,665 characters of intermediate data crosses the context window to produce a two-digit answer.

CLI, schema known 1,449 in · 96 out

Filters before anything reaches the model. 2 characters come back.

puzzle bee --letters VALIDTY --center V --json \
  | jq '[.words[] | select((.word|length) >= 5)] | length'
24

This generalises to any tool returning large results, which is most real tools. It is the strongest argument against MCP and it deserves to be made at full strength.

06 Does the CLI pick the wrong command?

MEASURED — 95/95 correct across every arm

No. Across all runs the CLI agent never once selected the wrong command. What it got wrong was the shape of the data coming back:

aggregate task — every distinct command the CLI arm ran

run 1  ... --json | jq '[.[] | select((.word // .) | length >= 5)] | length'   ← wrong path, hedged
run 1  ... --json | jq '.'                                                     ← dumped it to look
run 1  ... --json | jq '[.words[] | select(.word|length>=5)] | length'          ← correct
runs 2-5 ... --json | jq '[.words[] | select((.word|length) >= 5)] | length'    ← straight there

Three tool calls on the first run, two thereafter. MCP was one call every time, because the output schema was already in context. Once the shape is known, the CLI drops to 1,449 input tokens and a single call — the cli+schema arm.

So MCP's real win is narrower than advertised

It is not knowing which tool to call. It is knowing what comes back. The advantage lives on the output schema, not the invocation.

Honest caveat

We tested three conventionally-named commands. With forty ambiguously-named ones, selection accuracy would likely degrade — but it degrades for MCP too, which is exactly what §04 measures. The genuinely different risk is not accuracy, it is blast radius: MCP structurally cannot call a tool you did not expose; bash can construct a command that succeeds at something you never intended.

07 Two predictions that flipped

Both were written into the brief before the benchmark ran. Both were wrong. They are reported as observed rather than smoothed over, because a rigged comparison is worth nothing to an engineering audience.

Prediction: MCP wins on unfamiliar tasks, because it is self-describing

Wrong. On the un-briefed crossword task the CLI agent won — 1,377 against 2,548 input tokens — and never spent a turn on --help. It guessed the Unix convention and hedged in the same round-trip:

puzzle crossword --pattern "C_O__W_RD" --json 2>/dev/null || puzzle crossword --help

A conventionally-named CLI is itself a discovery mechanism. MCP’s self-description advantage would hold for unguessable enums or non-obvious required-field combinations — not for a well-named flag.

Prediction: with 40 commands the CLI’s discovery cost would climb

Wrong. On the unbriefed task the CLI at 40 commands (1,572 ± 470 input tokens) was no worse than at 3 (2,067 ± 1,090). Discovery cost is real — it lives in that spread, from runs that guessed a subcommand wrong — but it does not scale with catalogue size.

The traces say why: across all 30 CLI sweep runs, not one ran ls. The agent guesses puzzle crossword --pattern …, usually hedged with || puzzle --help in the same command, so the size of the directory never reaches it.

Limit on this finding

Forty well-named commands under one conventional entry point. Forty badly-named ones, or a task that forces enumeration, would very likely behave differently.

Prediction: the results would split, some tasks each

Wrong. The CLI won every task on tokens. There is no draw to report, so the conclusion does not manufacture one.

08 So when is MCP the right call?

A CLI is a tool you install. An MCP server is a service you deploy. Every architectural difference follows from that.

When…Why the CLI cannot do it
There is more than one consumerA CLI lives on a machine. Updating it means everyone reinstalls, and you cannot tell who is on which version. Updating a server is a deploy — every consumer gets it at once.
Non-engineers are consumersClaude Desktop cannot run your bash script. It can connect to your server. The entire “democratize” argument exists only on the MCP side.
You need enforceable permissionsYou cannot hand someone bash and withhold “run something I did not anticipate.” Handing over bash is handing over the machine. Depends() and schema scoping have no CLI equivalent.
You need one audit seamForty scripts across twelve laptops produce nothing. One server produces Part 02’s usage graph.
Credentials should not sit on laptopsThe server holds them; callers never see them.
Definitions must be canonicalThe server is where an organisation agrees what “qualified lead” means. That is Part 09.

The CLI wins for a single operator doing local, exploratory, composable work — which describes most individual engineering, and is why the token numbers came out the way they did.

The point to leave the room with

These are not competing on the same axis. The CLI’s efficiency is a runtime property. MCP’s advantages are organisational properties — versioning, access control, observability, reach. Choosing between them on token count alone is answering the wrong question.

The direction the field is heading, named here but deliberately not built: let the model write code that calls tools, so intermediate results never enter the context window at all. That collapses the composition gap without giving up the schema.

What is not measured

No prompt caching — which would materially reduce MCP’s repeated schema cost in production. Wall clock is dominated by API latency, not by either approach. Payloads here are small; the composition gap widens as results grow.
