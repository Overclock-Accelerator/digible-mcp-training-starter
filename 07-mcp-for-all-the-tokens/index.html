MCP Training · Part 07

MCP for all the tokens

One agent, five vendors’ MCP servers, 155 tools. We measured what the tool definitions cost per turn — and then tried hard to make the agent pick the wrong tool.

~4 min live 285 runs claude-sonnet-5 2026-08-31

01 The company that said yes five times

Nobody decides to give an agent 155 tools. It happens one reasonable server at a time.

The docs team connects the knowledge base. Support connects the helpdesk. Sales connects the CRM. Somebody notices the analytics vendor ships an MCP server too, and it is already paid for. Then the infrastructure platform, which ships everything it has.

#VendorDomainToolsCumulative

One agent connects to a growing prefix of that list — server 1, then 1+2, then 1+2+3 — through MultiServerMCPClient. The agent, the model and the prompts never change. The only variable is how many vendors are plugged in.

Each vendor is a separate long-running process, served over HTTP on its own port (8010–8014). Nothing spawns them; the agent connects by URL. Five vendors really is five processes, and you can tail -f one window to watch calls land on Bastion while you type in another.

Two questions, not one

Everyone expects this to cost tokens. The second question is the one that decides whether it also costs correctness: when five vendors independently ship a tool for “find a document”, does the agent still pick the right one?

02 Why it costs anything at all

A tool definition is not a pointer the client resolves at call time. It is text, serialized into the request body, on every single request, for the life of the conversation. Here is one, exactly as the model receives it:

python show_schema.py — one entry, verbatim

{
  "name": "search_docs",
  "description": "Full-text search across Northwind Docs pages. Northwind is
                  the company's internal engineering documentation platform;
                  page ids look like NW-4471.",
  "inputSchema": {
    "properties": {
      "agent_name": { "type": "string",
                      "description": "The name of the calling agent." },
      "query":      { "type": "string",
                      "description": "Search terms, e.g. \"database failover runbook\"." },
      "space":      { "type": "string", "default": "all",
                      "description": "Restrict to one Northwind space, or \"all\"." },
      "limit":      { "type": "integer", "default": 10,
                      "description": "Maximum number of pages to return." }
    },
    "required": ["agent_name", "query"]
  }
}

The sentence to say out loud

Sixty-nine thousand characters, re-sent on every turn. Not once at connection. Not once per conversation. Every turn, whether the agent calls one tool or none.

03 The collisions, planted on purpose

Five vendors independently solving “let the agent find a document” produce five different names for it. Nobody coordinated. Each name is defensible in isolation.

Twenty of the 155 tools are deliberate near-duplicates of Northwind’s five, spread one per rival server — exactly as they would be if five vendors each shipped their own:

Plus the classic three, one per server: create_ticket (Helios), open_issue (Meridian), file_bug (Bastion).

What is deliberately not tested

Real vendors collide outright — two servers both shipping search_docs is entirely plausible. langchain-mcp-adapters flattens every server into one flat namespace, so a true duplicate would silently shadow, and we would have measured the adapter rather than the model. catalog.py asserts name uniqueness at import. The collision problem is real; it is just not what these numbers are about.

04 How the experiment is controlled

Every correct answer lives on Northwind Docs, the server connected at every step. The right answer never moves. Only the pile of plausible wrong ones grows.

  • 15 tasks, each with exactly one correct tool, run at all five steps.
  • 3 runs per cell — single runs are noise, the model is sampled.
  • Token counts read from the Anthropic API’s own usage_metadata, summed across every round-trip. Nothing estimated.
  • Nothing in the system prompt says which vendor owns what. Everything the model needs is in the tool descriptions — which is the situation you are in the moment you connect a server somebody else configured.
  • 285 API calls total.

Tasks come in three tiers of difficulty:

TierWhat it doesExample
qualifiedNames the vendor. The answer is spelled out.“Search Northwind Docs for pages about the database failover runbook.”
impliedNever says “Northwind”. Identifies the target by the NW-#### id convention or Northwind’s own self-description.“What top-level groupings of pages exist in our internal engineering documentation platform?”
adversarialPhrased so a tool on another server keyword-matches better than the right one.“I need the failover runbook for the database. Find it for me.”
The trap in the adversarial tier

Bastion Infra ships failover_database — Fail a Bastion database over to a replica. The prompt says failover and database. The correct answer is search_docs, because the user asked for a runbook. A wrong pick here is not a token-efficiency problem; it is a production incident.

05 The tool-definition tax

The cleanest number in the folder comes from a prompt that calls no tool at all: “Reply with exactly the word READY.” One round-trip. Everything fixed except how many schemas were sent.

The headline

170–191 input tokens per tool per request — call it ~180 — near-flat across a 31x range in tool count. Connecting all five vendors costs 25,579 extra input tokens on every single turn, before the agent does any work at all.

It replicates

The MCP-vs-CLI folder in this series measured ~178 tokens per tool per request on a completely different single-server catalogue of word utilities. Different domain, different tools, same slope. The number travels.

The standard deviation is zero at every step, across all three runs. This is not an average you might get lucky on — the tool block is deterministic text. It is a fixed bill.

What it extrapolates to

07 Now the interesting half: does it get confused?

This is the question the MCP-vs-CLI folder could not answer, because it had three conventionally-named commands and nothing to confuse them with. Here, wrong selection is genuinely available — 20 planted near-duplicates and 130 more tools on top.

The finding

Zero calls to any of the 150 non-Northwind tools. Ever. Not a mis-selection, not an exploratory call, not a recovery. 150 tools sat in the context window costing 25,579 tokens a turn and were never once touched.

The only multi-call runs were 22 instances of search_docs → get_doc — find the page, then read it. That is correct chaining on a search task, not recovery from a bad pick. Round-trips stayed flat at 2.1 across every step.

Report this plainly, do not soften it

The cost of over-connecting MCP servers is tokens, not correctness. That is a cleaner and more useful argument than the one we went looking for. Nobody has to be talked out of a reliability scare; they have to be shown a bill.

08 What we tried, so nobody thinks we did not try

A 100% result is only worth anything if the test could plausibly have failed. Four escalations, in order:

  1. Plant near-duplicates across vendors

    Five names for “find a document”, five for “read one”, five for “list containers”, and so on — 20 planted collisions. No effect.

  2. Stop naming the vendor

    The implied tier never says “Northwind”. It leans on the NW-#### id convention or Northwind’s own self-description, so the model has to read descriptions rather than pattern-match a proper noun. No effect — 75/75.

  3. Make a rival tool the better keyword match

    The adversarial tier. “I need the failover runbook for the database” next to failover_database. “What documentation spaces do we have” next to list_doc_spaces, a near-identical name on another server. No effect — 75/75.

  4. Bury the right answers at the bottom of the list

    Position in a flat tool list is a known selection bias, and Northwind was registered first. The control reverses the order so the five correct tools sit after 150 others. No effect — 45/45.

What would be needed to break it

Genuine ambiguity, not more tools. Two tools whose descriptions are both honestly applicable to the request — at which point there is no correct answer to score against, and it is a spec problem rather than a selection problem. Or exact name collisions across servers, which the adapter resolves before the model ever sees them. Or a smaller model: this is one model on one task family, and that is a real limit on the finding.

Why it held up

Every Northwind description names Northwind. Description quality is selection accuracy, and these descriptions were written carefully — which is exactly the advice, and also exactly why the experiment did not break. A server that ships terse, vendor-anonymous descriptions is running a different experiment.

09 Do this one live instead

Every table above is an assertion. This is the thing itself — and it lets the room supply the request.

Running the agent with no arguments opens a conversation. Run it twice, ask the identical ambiguous thing, and watch the tool-call line rather than the prose:

the two commands

./start_servers.sh              # once, in another terminal
python agent.py --servers 1     # chat with 5 tools
python agent.py --servers 5     # chat with 155 tools

Take a suggestion from the floor. Something with no answer in the fixtures works best — here is find me the docs on rate limits, one run each:

5 tools 4 calls, one vendor

search_docs("rate limits")
search_docs("API rate limiting policy")
list_spaces()
search_docs("rate limit", space="Product")

Rewords the query, checks what spaces exist, tries again. All Northwind.

155 tools 3 calls, three vendors

search_documentation()   → Bastion Infra
search_docs()            → Northwind Docs
find_documents()         → Helios Helpdesk

Asks three different companies’ systems about an internal engineering topic, because three of them plausibly could have it.

What this is and is not

Both fan out when there is nothing to find. What changes at 155 tools is the direction — the search crosses vendor boundaries. This is one interactive run each, not a measurement: no repeats, no scoring, and an under-specified request has no right answer to score against. It is the honest complement to the 270/270 — well-specified requests do not degrade, under-specified ones spread out.

Also worth pointing at

Ask a follow-up the model can answer from memory — which of those is for engineering? — and the trace prints (none — the model answered without calling a tool). Knowing when not to call a tool is its own lesson.

Keep the two paths separate

The chat loop is for demonstration. Every number on this page comes from benchmark.py, which drives the agent function directly and never touches the interactive CLI. Nothing typed in a chat session is evidence.

10 What to actually do about it

Connect the servers a given agent needs. Not every server your company runs.

This is the whole practical takeaway, and it is unglamorous. There is no configuration flag that makes 155 tool definitions cheap. The tool block is text in the request, and text in the request costs tokens every turn.

Instead of…Do this
One agent with every company server attachedOne agent per job, each connected to the servers that job uses. A docs agent does not need the infra server.
Shipping every tool your platform hasShip the tools agents call. A server with 80 tools imposes 80 tools’ worth of tax on every consumer, forever.
“It’s already paid for, hook it up”Price the connection. ~180 input tokens per tool per turn is the exchange rate.
Terse descriptions to save tokensDo not. Descriptions are what selection accuracy is made of. Cut tools, not words.
The mitigation we did not measure

Prompt caching. Anthropic’s prompt caching can amortize a large static tool block across the turns of a session, cutting the repeat cost of cache hits substantially. That would soften this tax considerably — it would not eliminate it: the first request still pays in full, cache entries expire, and changing the tool set invalidates the block. It is the obvious follow-up experiment and it is not measured here. If someone raises it in the room, that is the honest answer.

The direction the field is moving

Load tool definitions on demand — as importable modules read from a filesystem rather than injected into every request — so the schema tax scales with what an agent actually uses instead of what it has installed. Anthropic has published this as “code execution with MCP”. It is the same conclusion the MCP-vs-CLI folder in this series arrived at from the other direction.

11 Caveats, stated plainly

  • One model. claude-sonnet-5 only. A smaller model would plausibly be more susceptible to near-duplicate confusion; this does not test that.
  • No prompt caching — the biggest missing measurement, named above.
  • Tool names are unique across the five servers, by construction, for the adapter reason in section 03. Real vendors collide outright.
  • Small payloads. Fixture responses are a few hundred bytes. Nothing here says how tool-result volume interacts with tool-definition volume.
  • Transport is not a variable. The numbers were measured over stdio; the servers now run over HTTP. The tool block sent to the API is byte-identical either way (69,578 chars both times) and all five tax-probe points reproduce to the digit, so the results were not re-run.
  • Wall clock is API latency. Reported for completeness, not for conclusions.
  • The 40-turn figures are extrapolation, not a measured 40-turn conversation. The per-turn number underneath them is measured.
  • The distractor tools were never called once across all 292 measured tool calls. That is the point: they cost their full schema anyway.
  • Section 09 is a demo, not data. One interactive run per side, unscored. It illustrates a behaviour; it does not measure one.
